# Lingxi LingXiCode Self Installer

This directory contains the first-party Windows installer for Lingxi LingXiCode.

The project no longer treats the old `electron-builder` NSIS `Setup.exe` as the official release artifact. The current official installer is generated by the self-installer pipeline and ends up here:

```text
installer\dist\灵犀 LingXiCode Installer 1.0.0.exe
```

## Why This Installer Exists

The project has two different kinds of data, and they must not be mixed:

- application binaries and runtime files
- user-selected project data and long-term project memory

The old generic installer flow made it too easy to confuse these two paths, which in turn caused mistakes around shortcut targets, uninstall registration, and release artifact naming.

The self-installer exists to make those rules explicit and stable.

In practice:

- `electron-builder` is only responsible for producing the unpacked app folder
- `installer\build-self-installer.ps1` turns that folder into the final installer
- `installer\LingxiInstaller\Installer.cs` defines the real install/uninstall behavior

## Build Principle

The build is a two-stage pipeline.

### Stage 1: App packaging

`npm run pack` runs `electron-builder --dir`.
This creates the unpacked Electron app at:

```text
dist\win-unpacked
```

This folder is the application payload source, not the final installer.

### Stage 2: Self-installer assembly

`installer\build-self-installer.ps1` takes `dist\win-unpacked`, compresses it into `installer\payload\app.zip`, then compiles a small .NET Framework bootstrapper into the final installer executable.

That bootstrapper embeds two resources:

- `app.zip` — the application payload
- `LingxiUninstall.exe` — the uninstall companion

The final installer is therefore self-contained.

## Script Map

Current `package.json` scripts:

- `npm run pack`
  - runs `electron-builder --dir`
  - produces `dist\win-unpacked`
- `npm run dist`
  - alias of `npm run dist:self`
  - this is the preferred release command
- `npm run dist:legacy`
  - runs the raw `electron-builder` release flow
  - kept only for backward compatibility and comparison
- `npm run dist:self`
  - runs `installer\build-self-installer.ps1`
  - this is the official release path
- `npm run dist:self:skip-pack`
  - skips `npm run pack`
  - use only when `dist\win-unpacked` is already current

## Required Environment

- Windows
- Node dependencies already installed with `npm install`
- `electron-builder` available from project dependencies
- .NET Framework compiler available at one of:
  - `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`
  - `C:\Windows\Microsoft.NET\Framework\v4.0.30319\csc.exe`

No .NET SDK is required. The installer is compiled with the built-in .NET Framework compiler.

The build may print `CS1607` warnings for WPF assemblies. Those warnings are non-blocking as long as the final installer exe is produced successfully.

Important rules:

- if `dist\win-unpacked` is missing, the self-installer cannot continue
- if the .NET Framework compiler is missing, the bootstrapper cannot be built
- `skip-pack` is only an optimization, not a substitute for a release build

## End-to-End Flow

`npm run dist:self` runs the following sequence:

1. Run `npm run pack`.
2. `electron-builder` creates the unpacked app at `dist\win-unpacked`.
3. `installer\build-self-installer.ps1` compresses that folder into `installer\payload\app.zip`.
4. The script compiles the uninstaller into `installer\dist\LingxiUninstall.exe`.
5. The script embeds both `app.zip` and `LingxiUninstall.exe` into `installer\dist\灵犀 LingXiCode Installer 1.0.0.exe`.

### Why each step matters

1. `npm run pack`
   - guarantees the app bundle is built from the current source tree
   - isolates app packaging from installer logic
2. `dist\win-unpacked`
   - is the actual runtime payload
   - prevents shipping raw source or development-only files
3. `app.zip`
   - gives the installer a stable embedded payload format
   - keeps the final exe self-contained
4. `LingxiUninstall.exe`
   - keeps uninstall logic versioned with the installer
   - avoids relying on external uninstall scripts
5. Final installer exe
   - is the only file that should be treated as the official release artifact

## Installer Behavior

The installer asks the user to choose two paths:

- Lingxi LingXiCode application install path
- Lingxi project data storage path

The app path receives the unpacked application files.

The selected project data path is written to:

```text
<install-dir>\lingxi-data-dir.txt
```

Project data includes:

- project list
- context
- ledger
- cache
- memory

Model API configuration is separate from project data and is stored under the current user's home directory:

```text
%USERPROFILE%\.lingxicode\api-config.json
```

This separation is intentional:

- project data follows the user-selected data storage path
- model API config stays in the user data directory
- projects remain isolated from each other

### Path-resolution principle

The installer should always prefer the user-selected project data path over any hardcoded fallback.

The packaged executable name must also match the installer's expectation, so shortcut and uninstall entries always point to the real binary.

That is why `package.json` now sets:

- `build.win.executableName = "lingxi-lingxicode"`

and the installer code expects:

- `lingxi-lingxicode.exe`

## Uninstall Behavior

The uninstaller is per-user and modernized to match the installer UI.

By default, uninstall removes the installed application files only.

Project data and model API config are removed only when the user explicitly checks the corresponding options in the uninstall UI.

The uninstall entry is also written into the Windows uninstall registry so the app can appear in system uninstall lists more reliably.

Because Windows may surface uninstall entries from different registry views, the installer attempts both the current-user path and the 32-bit machine view when registering uninstall information.

## Common Failure Points

If a future model needs to debug packaging, check these first:

1. Wrong executable name
   - shortcut points to an exe name that was never produced
   - symptom: shortcut says the app does not exist
2. Missing `dist\win-unpacked`
   - the self-installer has no payload to package
   - symptom: `Missing app output` or empty installer output
3. Missing .NET Framework compiler
   - installer bootstrapper cannot compile
   - symptom: `No .NET Framework csc.exe found`
4. Wrong script choice
   - using `dist:legacy` instead of `dist:self`
   - symptom: old NSIS artifact is produced instead of the self installer
5. Stale output reused with `skip-pack`
   - `dist\win-unpacked` is outdated
   - symptom: installer is built from old app files
6. Confusing build output with source
   - `dist\win-unpacked` is build output, not source
   - `installer\payload\app.zip` is an intermediate archive
   - `installer\dist\LingxiUninstall.exe` is generated too

## Release Checklist

Before sending an installer to users:

1. Run:

   ```powershell
   npm run dist
   ```

2. Confirm this file exists:

   ```text
   installer\dist\灵犀 LingXiCode Installer 1.0.0.exe
   ```

3. Confirm `dist\win-unpacked` was created during the build.
4. Confirm old NSIS release files are not being distributed.
5. Install into a clean directory.
6. Confirm the installer offers both application path and data path selection.
7. Launch Lingxi LingXiCode from the desktop or Start Menu shortcut.
8. Confirm the app name displays as `灵犀 LingXiCode`.
9. Uninstall once and confirm the uninstall UI works.
10. Confirm data removal options behave as expected.

## Notes For Future AI Maintainers

Be conservative when editing the installer.

- Keep installer source in `installer\LingxiInstaller\Installer.cs`.
- Keep build logic in `installer\build-self-installer.ps1`.
- Keep the official release command as `npm run dist` / `npm run dist:self`.
- Do not move model API config back into project storage.
- Do not hard-code user-specific data paths.
- Do not treat `dist\win-unpacked` as a release installer.
- Do not distribute old `Setup.exe` files from `dist`.
- Do not assume `skip-pack` is safe unless the unpacked app is fresh.

If changing the UI text, be careful with Chinese encoding. Prefer editing files directly as UTF-8 instead of generating Chinese text through shell heredocs.
