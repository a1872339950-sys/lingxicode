# TDD 开发

## 何时使用

- 用户要求 TDD / 先测后写
- 核心逻辑可测、有现成测试框架
- 修 bug 时适合先钉住回归用例

## 何时不用

- 纯 UI 微调且项目无测试基建、用户只要视觉结果
- 用户明确不要写测试

## 流程

1. **理解需求**：输入、输出、边界  
2. **红**：先写一个失败的测试，描述期望行为  
3. **绿**：写最少代码让测试通过  
4. **重构**：保持测试绿的前提下整理结构  
5. **迭代**：加场景、重复红绿重构  

## 原则

- 测试独立、尽量快、失败信息可读  
- 覆盖边界：空值、极限、异常路径  
- 不为了「覆盖率数字」写无意义断言  
- 实现完成后仍应用 `verify-before-done` 做整体核对
