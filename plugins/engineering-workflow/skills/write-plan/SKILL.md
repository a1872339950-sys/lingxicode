# 先写计划

## 何时使用

- 用户要求「先计划」「出方案再做」
- 任务跨多个模块、有技术选型或明显风险
- 实现前需要用户确认方向

## 不要使用

- 单文件小改、用户明确「直接改」
- 紧急热修且根因已钉死（可极短口述计划后立刻修）

## 流程

1. **只读取证**：搜入口、读关键片段、确认现有模式；不写仓库
2. **产出计划**：有序步骤，每步可验证；标出风险与备选
3. **请用户确认**：用 `confirm_plan` 或 `ask_user_choice`，不要只在正文里问「是否开始」
4. **确认后再实现**：进入实现后可用 `complete_step` 更新进度

## 好计划标准

- 步骤对应真实工程动作（改哪些边界、如何验证），不是空泛「分析→编码→测试」
- 单步一句话能做完检查：做完能否客观判定 done
- 写清不做什么，避免范围膨胀
- 需要用户拍板的点单独列为选项

## 差计划（避免）

- 只有三个空步骤：分析 / 写代码 / 测试
- 把未证实的猜测写成既定事实
- 计划里要求做当前环境做不到的事却不说明

## 与 Plan 模式

- 需要严格只读讨论时，可 `enter_plan_mode`
- 进度清单工具不能代替「用户确认执行」
