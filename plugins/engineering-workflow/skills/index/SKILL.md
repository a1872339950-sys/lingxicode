# 工程交付总入口

本插件把工程交付拆成可组合流程。**先分类，再进入对应子流程**；不要一上来就大面积改代码。

## 何时使用本包

- 实现 / 新增 / 重构功能
- 修复缺陷或排查后准备改代码
- 多文件、多步骤、需要验收的交付
- 用户说「按规范做」「别乱改」「先计划再写」

## 何时离开

- 纯问答、纯方案讨论且用户明确不要改代码
- 产物型任务（Office / 3D / 音乐工作台）→ 走对应能力，本包只约束「工程侧」部分

## 路由（先做这一步）

| 任务形态 | 走哪条 |
|----------|--------|
| 需求仍模糊、方案未定 | 澄清目标 → 需要时用 `write-plan` + `confirm_plan` / `ask_user_choice` |
| 已是明确缺陷 / 报错 | `systematic-debug`：复现 → 取证 → 根因 → 最小修复 → 验证 |
| 明确功能开发 | 定位入口与影响面 → 最小实现 → 验证；适合补测时用 `tdd` |
| 准备宣称完成 / 可合并 | **必须** `verify-before-done` |
| 会话要中断、交给下一轮 | `handoff` |

也可按用户点名直接进入子 Skill：`write-plan`、`systematic-debug`、`tdd`、`verify-before-done`、`handoff`。

## 硬规则

1. **用户明确指令优先**（包括「直接改」「不要 TDD」）
2. Plan / 方向未确认前：只读取证，不写仓库（用户已明确小改直做除外）
3. 改代码优先 `apply_patch` / `text_edit` 等既有编辑工具，保留恢复点
4. **不把「搜了很多文件」当成验证**；验证要对准本次改动的复现路径或检查命令
5. 主会话自己读流程说明；不要派子协作「代读 skill」
6. 对用户谈阶段与结果，少堆内部工具名与路径清单

## 阶段检查清单

| 阶段 | 完成标志 |
|------|----------|
| 定位 | 能指出真实入口文件/符号与为何改这里 |
| 实现 | 相关文件已改且与目标对齐 |
| 验证 | 至少一种：语法/项目检查/测试/运行态/手动复现 |
| 交付 | 用户能看懂改动、验证、风险；有代码改动则记操作备忘录 |

## 中途与收口

- 中途：用 `show_thinking_note` 说清当前阶段与下一刀（简短）
- 结束：结论优先，附验证与风险；不要空话收尾
- 有项目内代码改动：收尾前 `record_ai_operation_memo`（若可用）

## 与系统其他能力

- 网页落地页交付 → 用网页交付能力 / skill，不在本包硬套工程流水线
- 对话内示意图 → 解释清楚时用，不替代验证
