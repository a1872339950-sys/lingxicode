# 工程交付流水线

## 何时使用

- 实现/新增/重构功能
- 修复缺陷或排查后准备改代码
- 多文件、多步骤、需要验收的交付

## 何时离开

- 纯问答、纯方案讨论且用户明确不要改代码 → 不要强行进入实现阶段
- 产物型任务（PPT/3D/音乐）→ 走工作台与 `artifact_workflow`，本 skill 只约束「工程侧」部分

## 路由

1. **需求仍模糊、方案未定**  
   - 先澄清目标与边界；需要选型时用 Plan / `ask_user_choice` / `confirm_plan`  
   - 可配合技能：`write-plan`（多步计划）、`grill-me`（深挖需求）

2. **已是明确缺陷**  
   - 阶段：复现入口 → 根因 → 最小修复 → 验证  
   - 可配合：`systematic-debug`、`diagnose`（只读排查）、`tdd`（适合补测试时）

3. **明确功能开发**  
   - 阶段：定位入口与影响面 → 最小实现 → 分层验证 → 交付  
   - 可配合：`tdd`、`verify-before-done`

4. **实现已完成、准备收口**  
   - 必须走 `verify-before-done`：能跑的检查跑完再宣称完成  
   - 有项目内改动则 `record_ai_operation_memo`

## 硬规则

- Plan 未确认前：只读取证，不写仓库（用户已明确「直接改」且任务很小除外）
- 改代码优先 `apply_patch` / `text_edit` / 既有编辑工具，保留恢复点
- 不把「搜了很多文件」当成验证；验证要针对本次改动的复现路径或检查命令
- 主会话自己读 skill 说明；不要让子协作代替阅读流程

## 阶段检查清单（实现中）

| 阶段 | 完成标志 |
|------|----------|
| 定位 | 能指出真实入口文件/符号与为何改这里 |
| 实现 | 相关文件已改且与目标对齐 |
| 验证 | 至少一种：语法/项目检查/测试/运行态/手动复现路径 |
| 交付 | 用户能看懂改动、验证、风险；备忘录已记（如适用） |

## 输出

- 中途：用 `show_thinking_note` 说清当前阶段与下一刀
- 结束：结论优先，附验证与风险；不要空话收尾
