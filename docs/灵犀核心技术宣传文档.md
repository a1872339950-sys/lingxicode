# 灵犀 AI 工作台 — 核心技术解析

> 让 AI 从"一次性对话"进化为"可持续协作的开发伙伴"

---

## 概述

灵犀不是又一个套壳聊天框。它是一个深度集成在本地开发环境中的 AI 工作台，围绕三个核心技术构建：**AI 操作备忘录**（让 AI 的每一步改动可追溯）、**上下文压缩**（让长对话不会丢失记忆）、**多模态能力调度**（让不同模型各司其职）。

这三个系统协同工作，解决了 AI 辅助开发中最致命的三个问题：

- **黑盒问题**：AI 改了什么？为什么改？改完有没有残留风险？
- **遗忘问题**：聊了 50 轮之后，AI 还记得第 3 轮的结论吗？
- **能力错配问题**：让纯文本模型去分析图片，或者让慢模型去做简单任务。

---

## 一、AI 操作备忘录 — 让每一次 AI 改动可追溯

### 1.1 问题

你让 AI 帮你重构了一个模块，改了 7 个文件。第二天你想回看：改了哪些文件？哪些函数？验证了什么？有风险吗？

传统 AI 助手的答案是：不知道，去翻聊天记录吧。

灵犀的答案是：打开项目根目录下的 `.lingxi/ai-memos/timeline/`，每一轮改动都有结构化的备忘录。

### 1.2 设计原则

**项目隔离**：备忘录跟随项目保存，不写入软件全局数据目录。切换项目后，备忘录自动切换。

**事实优先**：文件变化（增删改）、diff 统计、快照信息由程序自动采集，AI 只补充人类可读的解释。不是 AI "觉得"改了什么，而是程序"看到"改了什么。

**默认不打扰**：每次 AI 改完项目文件后，不会自动保存备忘录，而是在聊天区用动画确认卡询问用户。用户选"保存"才进入项目发展史，选"不保存"则草稿自动清理。

**路径安全**：只采集项目根目录内的文件变化。项目外操作不记录真实路径，避免隐私泄露。

### 1.3 存储结构

```
项目根目录/.lingxi/ai-memos/
  drafts/                           ← 待用户确认的草稿
    memo-20260701-143012-session.md
  timeline/                         ← 用户确认后的正式备忘录
    memo-20260701-143012-session.md
  index.json                        ← 时间线索引，供安全快照中心快速读取
```

### 1.4 交互流程

```
AI 本轮任务结束
    ↓
采集本轮项目内文件变化（工具调用事件 + Git diff + 快照）
    ↓
有项目内文件变化？
  ├─ 否 → 不生成备忘录
  └─ 是 → 生成草稿到 drafts/
           ↓
        自动保存是否开启？
          ├─ 是 → 草稿自动转正到 timeline/
          └─ 否 → 聊天区显示动画确认卡
                   ├─ [保存] → 转正 + 更新索引
                   └─ [不保存] → 删除草稿
```

### 1.5 备忘录内容

每份备忘录包含：

- **任务目标**：用户本轮要求做什么
- **文件变化清单**：哪些文件被修改/新增/删除，增删行数统计
- **新增功能**：本轮新增了什么能力
- **修改功能**：本轮改了什么
- **删除或清理**：本轮删了什么
- **潜在残留风险**：AI 自我审查，标注不确定的地方
- **验证记录**：语法检查、自测结果
- **关联信息**：项目路径、分支、安全快照 ID

### 1.6 技术亮点

- **模块化架构**：后端拆分为 `collector.js`（事实采集）、`markdown.js`（文档生成）、`store.js`（持久化）、`settings.js`（偏好）、`ipc.js`（前后端通信），不堆进大文件。
- **安全快照联动**：备忘录记录安全快照 ID，后续可从备忘录直接回溯到 AI 改动前的状态。
- **索引机制**：`index.json` 维护时间线索引，安全快照中心和备忘录列表可快速读取，不需要遍历所有 Markdown 文件。

## 二、上下文压缩 — 让长对话永不遗忘

### 2.1 问题

和 AI 聊了 60 轮，上下文窗口满了。传统方案是截断旧消息，AI 就"失忆"了。

灵犀的方案是：把旧消息压缩成结构化摘要，注入上下文。AI 既能"看到"最近的完整对话，又能通过摘要"回忆"更早的关键结论。

### 2.2 核心机制

**触发策略**：每 8 轮（可配置）自动触发一次压缩。保留最近 4 轮原文不动，对更早的轮次生成摘要。

**双层摘要生成**：

1. **Worker 模型摘要**（优先）：调用配置的轻量模型，用结构化 prompt 让它输出 JSON 格式的摘要，包含主题、AI 做了什么、关键信息、未完成项。
2. **本地提取摘要**（兜底）：如果 Worker 模型不可用或返回失败，用正则提取 AI 回复中的高信号行（"完成了""修复了""原因是""风险"等关键词匹配），组装成摘要。

**摘要结构**：

```json
{
  "topic": "这 8 轮的共同主题，1 句话",
  "aiDid": ["AI 实际做了什么"],
  "keyInfo": ["后续任务需要知道的关键事实"],
  "openItems": ["还没完成、待确认的事项"]
}
```

**上下文注入**：最近 3 个压缩摘要注入上下文，更早的摘要自动封存。AI 需要旧细节时，可以通过 `recall_history` 工具按 ID 查询。

### 2.3 可视化：Context Compression Stack

输入框底部有一个"历史压缩"指示器，用彩色条带展示压缩层级：

- **灰色条**：已压缩的摘要层
- **橙色条**：最近保留原文层
- **紫色条**：缓冲中，还差 N 轮生成新摘要

点击可展开弹窗，查看每个压缩层的详细信息：轮次范围、主题、AI 做了什么、关键信息、未完成项。

### 2.4 聊天区状态卡

当压缩正在进行时，聊天区会显示一个状态卡：

- **进行中**：带旋转图标的"正在整理上下文中"，实时显示已用时间
- **完成**：带勾号的"上下文已压缩完成"，显示用时后淡出
- **失败**：带叉号的"上下文压缩失败，已跳过"

这个状态卡保证在 AI 思考/工具调用/回复卡片出现之前完成展示并淡出，不干扰用户。

### 2.5 技术亮点

- **原子写入**：压缩摘要保存时使用临时文件 + rename，避免写入中途崩溃导致数据损坏。
- **文件缓存**：`summaryFileCache` 使用 mtime + size 双重校验，避免频繁磁盘读写。
- **历史消息不丢失**：压缩后，原始聊天记录仍在当前窗口可见。AI 后续通过摘要和记忆查询继续工作。
- **可配置参数**：触发轮数、保留最近轮数、注入摘要数量均可调整。

## 三、多模态能力调度 — 让模型各司其职

### 3.1 问题

你配置了 3 个模型：一个做主力对话，一个擅长看图，一个擅长生图。当 AI 需要看一张图片时，应该自动切换到视觉模型；当需要生成图片时，应该切换到生图模型。但大多数 AI 工具只会用你指定的那个模型做所有事情。

灵犀的方案是：每个模型声明自己具备哪些能力，系统根据任务类型自动调度到具备对应能力的模型。

### 3.2 六种能力声明

每个模型可以声明以下能力：

| 能力 | 说明 |
|------|------|
| `text` | 文本对话（默认开启） |
| `vision` | 视觉理解，分析图片内容 |
| `imageGeneration` | 图片生成 |
| `musicGeneration` | 音乐生成 |
| `videoGeneration` | 视频生成 |
| `toolCalling` | 工具调用（默认开启） |

用户在模型设置中为每个模型勾选对应能力。系统自动维护一份标准化的能力声明。

### 3.3 能力路由

当 AI 需要某个能力时（比如用户上传了图片需要分析），系统执行以下调度逻辑：

1. **读取用户配置的路由优先级**：用户可以在设置中为每种能力指定模型优先级顺序。
2. **按优先级查找**：遍历用户配置的模型列表，找到第一个具备该能力且可用的模型。
3. **降级到当前模型**：如果用户没有配置路由，检查当前对话模型是否具备该能力。
4. **降级到任意可用模型**：如果当前模型不具备，从所有已配置模型中找到第一个具备该能力的。

```
用户配置的路由顺序
    ↓ 未配置
当前对话模型具备该能力？
    ↓ 不具备
所有模型中找到第一个具备的
    ↓ 都没有
返回错误：没有可用模型
```

### 3.4 视觉理解的权限机制

视觉理解涉及用户隐私（图片可能包含敏感内容），所以灵犀设计了一套权限机制：

- **当前模型就是视觉模型**：直接分析，无需额外确认。
- **需要切换到其他视觉模型**：弹窗询问用户"是否借用 [模型名] 分析此图片"。
- **用户可以配置策略**：每次询问 / 同模型自动允许 / 全部自动允许。

### 3.5 工具网关：三层调度

所有工具调用都经过一个统一的工具网关（Tool Gateway），按以下优先级分发：

1. **Office 层**：轻量级、无需项目上下文的工具（如文档查询）。
2. **Registry 层**：注册在工具注册表中的标准工具，每个工具有独立的 handler 模块。
3. **Legacy 层**：尚未迁移到注册表的旧工具。

这种分层设计让工具系统可以渐进式重构，不需要一次性迁移所有工具。

### 3.6 技术亮点

- **模型配置标准化**：`normalizeModel()` 统一处理不同来源的模型配置（内置模型、自定义模型、API 返回的模型），确保能力声明格式一致。
- **凭证校验**：调度前检查模型是否有有效的 API Key 或内置令牌，避免选中一个无法调用的模型。
- **路由键去重**：`getModelRoutingKey()` 用 `provider::apiUrl::modelId::modelName` 四段组合生成唯一键，避免不同配置的模型被误判为同一个。
- **内置模型 + 自定义模型统一搜索**：`findCapabilityModel()` 同时搜索内置模型列表和用户自定义模型列表，找到第一个符合条件的。

## 四、三个系统如何协同

这三个系统不是孤立的，它们共同构成了灵犀的"可持续开发协作"能力：

```
用户：帮我重构这个模块
    ↓
多模态调度：当前模型具备 toolCalling → 使用当前模型
    ↓
AI 执行任务，修改了 5 个文件
    ↓
上下文压缩：第 32 轮，触发第 4 次压缩，摘要"重构支付模块"
    ↓
AI 操作备忘录：采集文件变化 → 生成草稿 → 询问用户是否保存
    ↓
用户：保存
    ↓
备忘录进入 timeline，索引更新
    ↓
下一轮对话开始，AI 通过压缩摘要回忆"重构支付模块"的上下文
    ↓
用户：刚才那个接口改坏了
    ↓
AI 通过 recall_history 查询备忘录，定位到具体文件和改动
```

---

## 五、总结

灵犀不是一个"聊天 + 代码补全"的简单组合。它的三个核心技术分别解决了：

- **可追溯性**：AI 操作备忘录让每一轮改动都有迹可循，不再是黑盒。
- **持久记忆**：上下文压缩让 AI 在长对话中保持对关键信息的感知，不会"失忆"。
- **能力弹性**：多模态能力调度让不同模型各司其职，不浪费每个模型的长处。

这三个系统让 AI 从"一次性问答工具"进化为"可持续协作的开发伙伴"——它记得你做过什么，知道现在该做什么，能用最合适的工具完成任务。
